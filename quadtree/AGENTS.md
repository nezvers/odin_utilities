# quadtree: notes for agents

What is not obvious from the code of this library. The rules that hold for every library, the commands and the map of the libraries are in [../AGENTS.md](../AGENTS.md); the user facing description is in README.md.

- Two trees in one package. `quadtree.odin` is the main one, immediate mode (the user asked for it): cleared and filled again every frame, no handle map, no remove, no move, no cleanup; an element is `{rect, item, stamp}` in a plain array and the caller's `Item` (an index into the caller's array) is what a query returns. `quadtree_retained.odin` (`QuadtreeRetained*`, own `RetainedElement`/`RetainedLink`/`retained*` helpers) is the earlier retained version on `core:container/handle_map` (Add/Remove/Move/Cleanup, stable `Handle`), kept as an extension; it shares `Rect`, `Node`, `Area`, `quadrants`, `areaChild` and `QuadtreeNodeProc`. Do not mix the two features: immediate stays free of handles.
- `quadtree_chunks.odin` (`QuadtreeChunks($W,$H,$E,$N,$L)`, tests `quadtree_chunks_test.odin`) is a ring of W x H chunks, one immediate `Quadtree` each in LOCAL f32 coordinates, world positions f64. An item lives in exactly one chunk (the one with its top left corner) and may stick out by `max_item_size` (loose grid): so inserts never copy, queries grow the rectangle by `max_item_size` to pick the chunks and never see duplicates (no dedupe code). Slot = (cx mod W, cy mod H); `chunk.loaded` plus the stored cx, cy tell if a coordinate is really loaded. Query rectangles that cover more chunks than there are slots walk the slots instead of the coordinates. Local rectangles are computed as f64 subtraction then f32. The tree of a chunk is re-initialised on load, `Stream` unloads before it loads (slot conflicts). Demo `demo_chunks.odin` (items are indices into a ring sized array, content generated from the chunk coordinate).
- `quadtree.odin` (`Quadtree($E,$N,$L)`: `elements`, `nodes` (root + groups of 4, bump allocated, never freed until the next clear), `links` (a leaf's elements); `Quadtree*` procs), `quadtree_test.odin` and `quadtree_retained_test.odin` (`odin test quadtree`, brute force comparisons). Demos in `demo_common/` (collision, hover circles, bouncing balls on the immediate tree, `demo_retained.odin` on the retained one, `demo_chunks.odin` on the chunked world, `demo_rays.odin` ray cast, radius and nearest queries checked against a sampled brute force), thin starters in `demo_raylib/` and `demo_karl2d/`. Reference port source: `references/quadtree` (git ignored, the C code; its clone URL over ssh does not work here, use https).
- A split cannot fail half way: `leafSplit` runs only when `L - links_in_use >= 3 * count` (worst case every element in four children, minus the links it frees) and a group of four nodes is free; the elements of a split are added without splitting again (`may_split = false`). A leaf that cannot split just holds more and tries again at the next insert.
- `nodeAdd` that fails (links out) is undone with `nodeRemove` (used only for this), which skips leaves that do not hold the element and gives the links to the `link_free` list; so a failed `QuadtreeInsert` leaves the tree as it was (a split that happened stays, it is consistent).
- Descent compares only against the centre of the node (`quadrants`), so rectangles outside of `bounds` land in the border leaves and are still found.
- `quadtree_shape.odin` holds what the three trees share for shapes: `Probe` (rect, point, circle, segment), `probeHitsExtent` (pruning a node) and `probeHitsRect` (testing an element), the slab test `segmentBox`, and `QuerySession`. Rectangle and point queries still pick nodes with `quadrants` (centre compare); circles and segments carry the BOX of the node down (`extentChild`, outer edges at +-max(f32) so elements outside of the bounds, which sit in the border leaves, are still found). A segment that touches an edge hits; a circle that touches does not (strict `<`), like `RectOverlaps`. `SegmentFirst` visits an element once per leaf it is in: harmless for a minimum, and it needs no marks, so no session. Chunks convert the probe per chunk (`chunksProbeLocal`: f64 subtraction of the chunk corner, then f32) and skip chunks the shape cannot reach (`chunkReachable`: the chunk square grown by `max_item_size`). Tests: `quadtree_shape_test.odin` (independent brute force: edge crossings, not the slab method; a four thread test of sessions; the chunked test a million units from the origin).
- Rectangle and point queries of the immediate tree use no marks: `leafQueryOwned` reports an element only in the leaf that contains the top left corner of (element rect and query rect) overlap, tested against the leaf box (`low`, `high` extents, owner rule `low < corner <= high`, the same compare as `quadrants`). `Link` and `RetainedLink` carry a copy of the element rect for that test (so a leaf scan touches only links; an element or a handle map slot is read on a hit). The retained tree uses the same rule (`retainedLeafQueryOwned`). Only circle and segment queries use stamps. `nodeAdd`, `retainedNodeAdd`, `nodeQuery` and `retainedNodeQuery` follow a rectangle that fits one quadrant in a loop and recurse only where it reaches several: that alone made the build 2.7x faster (the recursion and the four way `quadrants` test were the cost), so keep that shape when changing them. Measured: marks were only a small part of the cost; the grid is still faster (descent depth and the scattered links).
- Nearest (`nodeNearest`, `retainedNodeNearest`, `QuadtreeChunksNearest`; helpers `Nearest($T)`, `nearestWants`, `nearestAdd`, `nearestChildren` in quadtree_shape.odin): depth first, children nearest first by the distance to their extent box, pruned by the k-th best; duplicates (an element in two leaves) are caught by a linear scan of the short result list instead of marks, so no writes. Distances are squared while searching and `nearestFinish` takes the roots (non generic on purpose: a generic proc is not checked until used). The chunked version sorts the loaded chunks by the distance to their box grown by `max_item_size` to the right and down and stops when a box is farther than the k-th best; distances of different chunks are comparable because each is measured from the point in that chunk's local frame.
- `quadtree_iterator.odin`: `QueryIterator` (explicit stack of `IteratorFrame`, depth at most `QUADTREE_MAX_DEPTH + 2`, the link of the leaf being scanned, the leaf box for the ownership test) shared by the immediate and the retained tree through one duck typed `iteratorNext(tree: ^$T)` (both have `nodes` and links with `next` and `rect`); the wrappers turn the link into an item or a handle and apply `omit`. It works only because rectangle queries need no marks. The chunked iterator keeps the coordinate (or slot) walk of `chunksQuery` as state and starts an inner iterator per chunk; it stores the slot of the current chunk, not a pointer, so it stays a plain value.
- `QuadtreeRetainedMove` first tries `retainedNodeResize`: when the old and the new rectangle reach exactly the same leaves (same quadrant masks at every branch) only the rect copies in the links of the element are rewritten (no unlink, link or split). A failed attempt may leave some links with the new rectangle: harmless, the fallback unlinks by handle. What is left of the cost is cache misses in the link lists (about 165 ns a move at 50k), so the next step would be a contiguous leaf layout, not more code in Move.
- `QuadtreeCompact`, `QuadtreeRetainedCompact`, `QuadtreeChunksCompact`: copy the links of the leaves into the caller's scratch in depth first leaf order (next = index + 1, last = -1, the leaf `first` repointed), copy back, reset `link_used` and the free list (asserts that the walk found exactly `links_in_use`). Found by an experiment before any layout redesign: contiguous leaves are worth 10 to 20% on queries, a rewrite of the leaf storage (buckets of entries) was not needed. `Link` and `RetainedLink` are public only for the scratch type.
- `kit/quadtree_kit.odin` (package `quadtree_kit`, the convention of `tilemap/kit`): the shared debug draw (`DrawQuadtree`, `DrawQuadtreeRetained`, `DrawQuadtreeChunks`, `DrawLeaf`); all demos draw their tree through it (the old `demo_common/tree_view.odin` is gone). The chunked one takes a camera center and a screen center and subtracts in f64.
- Tried and dropped: a bulk build `QuadtreeBuild(tree, rects, scratch)` (top down partition of the whole array, two passes per level, the quadrant mask kept in the top bits of the list entry, leaf links written contiguously). Correct, but 4.3 ms at 50k before the mask trick and 3.2 after, against 2.8 for insert plus `QuadtreeCompact` (uniform; clustered 3.35 against 3.2): each level looks at every element twice and that costs as much as the re-adding of the splits it saves. Do not try it again without a new idea (e.g. a Morton sort).
- Queries (circles, segments) mark elements with `stamp` (an element sits in several leaves) instead of a temp buffer; `QuadtreeClear` resets the counter, new elements start at 0. With a `QuerySession` the marks live in the caller's stamps (index = element index, or the slot `idx` of a retained handle) and the tree is not written: that is the thread safe path.
- `tool/bench` (`odin run quadtree/tool/bench -o:speed`, `-- --quick`) compares against a counting sort uniform grid, `grid_collision_map` (cells of 32, 64 per cell: it drops items on clustered scenes, the tool prints how many) and brute force; every structure must report equal neighbour counts (a MISMATCH line is a bug). Numbers and conclusions are in README. A debug build says nothing about speed.
- Demos: the script of each is run headless (`odin test quadtree/demo_common`) and in a window through the captures tool (`odin run demo_kit/tool/captures -- --karl2d quadtree`: the windows open on the second display, BenQ DL2215, from `demo_kit/monitor.txt`; never `-define:DEMO_TEST=true` by hand, it opens on the default display). Seven pictures per backend (`demo_common/captures/`: collision_wall, hover_picked, balls_running, retained_moving, chunks_hover, chunks_far, rays_diagonal), `-- --update` replaces them after an intended change of what a demo draws; a Capture needs a Wait behind it. Each demo keeps its objects in fixed arrays (wall grid, circles with a free slot list, balls) and rebuilds the tree from them once per frame; hover and collision rebuild after the edits, balls after moving and before the pair tests.
