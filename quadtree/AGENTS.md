# quadtree: notes for agents

What is not obvious from the code of this library. The rules that hold for every library, the commands and the map of the libraries are in [../AGENTS.md](../AGENTS.md); the user facing description is in README.md.

- Two trees in one package. `quadtree.odin` is the main one, immediate mode (the user asked for it): cleared and filled again every frame, no handle map, no remove, no move, no cleanup; an element is `{rect, item, stamp}` in a plain array and the caller's `Item` (an index into the caller's array) is what a query returns. `quadtree_retained.odin` (`QuadtreeRetained*`, own `RetainedElement`/`RetainedLink`/`retained*` helpers) is the earlier retained version on `core:container/handle_map` (Add/Remove/Move/Cleanup, stable `Handle`), kept as an extension; it shares `Rect`, `Node`, `Area`, `quadrants`, `areaChild` and `QuadtreeNodeProc`. Do not mix the two features: immediate stays free of handles.
- `quadtree_chunks.odin` (`QuadtreeChunks($W,$H,$E,$N,$L)`, tests `quadtree_chunks_test.odin`) is a ring of W x H chunks, one immediate `Quadtree` each in LOCAL f32 coordinates, world positions f64. An item lives in exactly one chunk (the one with its top left corner) and may stick out by `max_item_size` (loose grid): so inserts never copy, queries grow the rectangle by `max_item_size` to pick the chunks and never see duplicates (no dedupe code). Slot = (cx mod W, cy mod H); `chunk.loaded` plus the stored cx, cy tell if a coordinate is really loaded. Query rectangles that cover more chunks than there are slots walk the slots instead of the coordinates. Local rectangles are computed as f64 subtraction then f32. The tree of a chunk is re-initialised on load, `Stream` unloads before it loads (slot conflicts). Demo `demo_chunks.odin` (items are indices into a ring sized array, content generated from the chunk coordinate).
- `quadtree.odin` (`Quadtree($E,$N,$L)`: `elements`, `nodes` (root + groups of 4, bump allocated, never freed until the next clear), `links` (a leaf's elements); `Quadtree*` procs), `quadtree_test.odin` and `quadtree_retained_test.odin` (`odin test quadtree`, brute force comparisons). Demos in `demo_common/` (collision, hover circles, bouncing balls on the immediate tree, `demo_retained.odin` on the retained one, `demo_chunks.odin` on the chunked world), thin starters in `demo_raylib/` and `demo_karl2d/`. Reference port source: `references/quadtree` (git ignored, the C code; its clone URL over ssh does not work here, use https).
- A split cannot fail half way: `leafSplit` runs only when `L - links_in_use >= 3 * count` (worst case every element in four children, minus the links it frees) and a group of four nodes is free; the elements of a split are added without splitting again (`may_split = false`). A leaf that cannot split just holds more and tries again at the next insert.
- `nodeAdd` that fails (links out) is undone with `nodeRemove` (used only for this), which skips leaves that do not hold the element and gives the links to the `link_free` list; so a failed `QuadtreeInsert` leaves the tree as it was (a split that happened stays, it is consistent).
- Descent compares only against the centre of the node (`quadrants`), so rectangles outside of `bounds` land in the border leaves and are still found.
- Queries mark elements with `stamp` (an element sits in several leaves) instead of a temp buffer; `QuadtreeClear` resets the counter, new elements start at 0.
- Demos: the script of each is run headless (`odin test quadtree/demo_common`) and in a window (`odin run quadtree/demo_karl2d -define:DEMO_TEST=true`, both pass). Each demo keeps its objects in fixed arrays (wall grid, circles with a free slot list, balls) and rebuilds the tree from them once per frame; hover and collision rebuild after the edits, balls after moving and before the pair tests.
