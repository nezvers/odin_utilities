# odin_utilities

A collection of Odin libraries.
One library per directory, all with the same structure so any of them is a reference and a template (`templates/library`).
Shared assets: `assets/` (textures, fonts, sounds, gltf). `references/` is git ignored space for local checkouts of projects a library was ported from or follows (Clay, Dear ImGui). `karl2d/` is the Karl2D checkout that the `glue_karl2d` packages import by relative path (a directory junction or a clone, see Repository map).
Stale build outputs in a library folder (`demo.exe`, `*.pdb`, `log.txt`) are git ignored.

## Library structure (every odin_utilities library, template in odin_utilities/templates/library)
```
<lib>/  README.md  <lib>.odin (+ more files)  <lib>_test.odin (#+build !js when the lib builds for web, else tests at the bottom of the tested file)
        glue_raylib/<lib>_raylib.odin  glue_karl2d/<lib>_karl2d.odin   (glue, only what needs the framework)
        demo_common/   demos written ONCE against odin_utilities/demo_kit: one file per demo (`kit.Demo` with init/finit/update/draw/script), demos.odin lists them,
                       demo_common_test.odin plays the scripts headless
        demo_raylib/main.odin   one call: kit_raylib.Run("<lib>", demo_common.demos[:])
        demo_karl2d/main.odin   one call: kit_karl2d.Run("<lib>", demo_common.demos[:])
        .vscode/       launch.json, tasks.json, settings.json: REQUIRED, see below
```
- **Every library has a `.vscode/` folder** (`launch.json`, `tasks.json`, `settings.json` with `"project_name": "demo"`; the executables are git ignored), so that opening the library folder in VS Code runs and debugs what it has. Copy
  `templates/library/.vscode` and keep what applies: `Run Debug` / `Run Release` for `demo_raylib`, `Run Debug Karl2D` / `Run Release Karl2D` for `demo_karl2d` (a library with only one of them keeps only those),
  one `Build <Tool>` task and `Run <tool> (...)` configurations with the usual arguments for every program in `tool/<name>` (see `reports`, `ai_messaging`, `p2p`), and `Debug Tests` (a task that builds the tests with
  `odin build . -build-mode:test -debug -out:${config:project_name}_test.exe` and a configuration that runs that executable under the debugger, so breakpoints work inside tests) plus the tasks `Test` and `Check`:
  all libraries without demos have at least `Debug Tests`. Tasks run in the library folder (`cwd` = `${workspaceFolder}`), build with `-strict-style -vet`, and have the `.bin` variants for Linux and macOS like the others.
  A new library, a new demo or a new tool is not finished until its `.vscode` runs it (try the task once).
- Every library keeps its raylib demo in `demo_raylib/` (package `demo_raylib`) and its karl2d demo in `demo_karl2d/`, both thin. VS Code tasks build with `-out:${config:project_name}.exe` (`project_name` = `demo`).
- A demo that needs something the kit does not have (3D, a framework specific draw proc) puts the framework part in an extra file of `demo_raylib/` / `demo_karl2d/` and hooks it into demo_common (see fps_controller: `SceneDrawer`). The Karl2D 3D demo needs the custom fork, said in that README.
- A library that draws (tilemap, box2d_odin debug draw) also gets a `kit/` glue package (`tilemap/kit`, `box2d_odin/kit`: package `<lib>_kit`) that draws through `kit.Context`, so its demos stay in demo_common. Glue that is only for one framework (input, scene loaders, mic_meter) is reached from demo_common through an adapter table or the demo lives in `demo_<framework>/`.
- Non visual libraries (serial, task, web_serve) have no demos.

## demo_kit (odin_utilities/demo_kit)
- `Backend` (table of procs: shapes, text, textures, sound, camera, clip, mouse capture) implemented by `demo_kit/glue_raylib`, `demo_kit/glue_karl2d` and `HeadlessInit` (no window, drawing is counted). `Input` is plain data per frame, `Context` is what a demo proc gets. `gui.odin` has Button/Toggle/Slider/Spinner.
- Runtime tests: a demo's `script` is a `[]kit.Step` (Wait, Tap, Hold, Click, Drag, MoveTo, Scroll, LookBy, Type, Check(proc, message)); a Player turns it into input. Constructors are contextless so a script can be a global. `odin test <lib>/demo_common` runs it headless, `odin run <lib>/demo_raylib -define:DEMO_TEST=true` plays it in the window (exit code 1 on a failed check). A demo without script is a 60 frame smoke test.
- Screen capture tests: script step `kit.Capture("name")` compares the drawn frame with `captures/<backend>/<name>.png` next to the script file; only in a window with `-define:DEMO_CAPTURE=true` (new goldens are written when missing, `-define:DEMO_CAPTURE_UPDATE=true` replaces them). Headless skips it. `odin run demo_kit/tool/captures` (from odin_utilities; `-- ui reports`, `-- --karl2d`, `-- --update ui`, `-- --allow-new`, `-- --monitor <name>`) runs them for every library that has Capture steps and exits 1 on a changed picture, 2 on a new one: run it before committing a change to drawing, text layout or a style, and look at every `.actual.png` it leaves. The windows go to the display named by `--monitor`, `DEMO_MONITOR` or the local file `demo_kit/monitor.txt` (git ignored), with a size that does not depend on the scaling of the display (Karl2D `disable_auto_scale_hint`, raylib resized after it moved): the goldens are 1280 x 720 on every display. See demo_kit/README.md.
- Strings with apostrophes break multi file bash heredocs here: write demo files with the Write tool.

## Repository map
- `<lib>/` - one library per directory (tilemap, input, tween, timer, ui, sprite, ...).
- karl2d - a checkout of a Karl2D fork (upstream plus the embed commits and the 3D layer, branch render3d), not part of these libraries; it has its own rules.
- Libraries import karl2d by relative path, e.g. `import "../../karl2d"` from tilemap/glue_karl2d.

## Library style (see tilemap as reference)
- Libraries are framework agnostic. Framework specific drawing lives in sub packages (`glue_raylib/`, `glue_karl2d/`) named `<lib>_<framework>.odin`.
- No hidden allocations: user provides buffers/slices (`TilemapInit(position, size, tile_size, buffer)`).
- Procedures are PascalCase prefixed by the abstraction: `TilemapGetTile`, `TileAtlasInit`, `AutotileRuleUpdateCell`, `DualGridUpdateTilemap`. Constants are UPPER_CASE (`TILE_EMPTY`). Types are PascalCase.
- Typed locals: `name:Type = value`. `assert` for preconditions. Comments describe each proc and non-obvious steps.
- Demo code uses snake_case procs.
- A feature that uses data + derived output takes input and output tilemaps (see `rule_tile.odin`, `dual_grid.odin`).
- Keep comments in the code; explain why, not what.

## tilemap library layout
- Core: `common.odin` (types), `tilemap.odin`, `tileset.odin`, `tile.odin`, `tile_atlas.odin`, `rule_tile.odin`, `dual_grid.odin`, `editing.odin` (input helpers + paint/drag/select), `rand.odin`.
- TileID 0 is TILE_EMPTY, 255 is TILE_INVALID. Chain: Tilemap (grid of TileID) -> Tileset -> Tile (alternatives) -> TileAtlas (texture positions).
- `glue_raylib/tilemap_raylib.odin`, `glue_karl2d/tilemap_karl2d.odin` - Draw* procs.
- `demo_raylib/` - raylib demo (`odin run demo_raylib`, Odin package `demo_raylib`). Each demo file is `#+private file` with `@(private="package") state_xxx:State = {enter, exit, update, draw}`; register in `demo_raylib/demo.odin` (`state_list`, `Example` enum, `example_names`).
- `demo_karl2d/` - same demos for karl2d (`odin run demo_karl2d`); files in `demo_karl2d/game/`, states are `GameState{init, finit, update, draw}`, register in `game_state.odin` (`state_list`, `StateIndex`).
- Shared demo data (atlas/tile/tilemap buffers, textures) is in each `demo_common.odin`; demo executables set working dir to exe dir, raylib demo loads `../assets/textures/...`, karl2d demo embeds with `#load`.
- To port an example: put reusable logic in the library package, keep only input/drawing in the two demos.

## tween library layout
- `tween.odin` (Tween + Step builder + `TweenUpdate`), `tween_value.odin` (property types), `tween_system.odin` (static pool `TweenSystem($N)`, `System*` procs), `tween_test.odin` (`odin test .`).
- Zero allocations: fixed step array per Tween, handle-map pool. Demos in `demo_raylib/` (raylib) and `demo_karl2d/game/` follow the same state pattern as tilemap.

## grid_collision_map library layout
- `grid_collision_map.odin` (`GridMap($X,$Y,$N,$C)`: colliders in `hm.Static_Handle_Map`, per cell fixed `Slot` of Handles; `GridMap*` procs, `Rect*` narrow phase helpers), `grid_collision_map_test.odin` (`odin test .`). Demos in `demo_raylib/` and `demo_karl2d/game/` (`demo_collision.odin`).
- Same "fixed buffers, fail instead of grow" rule as tilemap/tween.

## microui library layout
- `microui.odin` (package `microui_utils`: `MuiLog`, `U8Slider`, `AtlasToRGBA`), glue `glue_raylib/microui_raylib.odin` and `glue_karl2d/microui_karl2d.odin` (`Init/Update/Render/Cleanup` on a user owned `MuiState`), demos `demo_raylib/` and `demo_karl2d/game/` (`demo_microui.odin`).

## atlas_packer library layout
- `atlas_packer.odin` (`AtlasPacker` of slices, `Init(packer, atlas_size, rect_capacity, allocator)`), `font.odin` (`FontInit/GetFontRects/RenderGlyph`: glyph bitmaps at one pixel height through the `font` library, its parser and its exact coverage rasterizer, no stb_truetype; `RenderGlyph(font, glyph, alpha, curves)` takes optional room for outlines of more than `GLYPH_CURVES` curves), glue `glue_raylib/` and `glue_karl2d/` (`BakeImageRects`, `CreateImage`, `BakeFontGlyphs`, `RegisterFont`), `atlas_packer_test.odin` (`odin test .`).
- Allocator agnostic: demos use `mem.Arena` over a static buffer, persistent allocations first, then `begin_arena_temp_memory` section for source images, `arena_free_all` in finit.

## box2d_odin library layout
- Library (`package box2d_odin`): `helpers.odin` (Add* shape wrappers, Create* body/joint helpers), `camera.odin`, `input.odin`, `ui.odin` (immediate mode UI over a `Backend`), `sample.odin` (`Sample` + `SampleHost`), glue in `glue_raylib/` and `glue_karl2d/` (`InitDebugDraw`).
- `samples/` ports `box2d/samples/sample_*.cpp` (one file each, registered with `@(init)`, file private globals as state). `odin test samples` smoke tests every sample headless. Demos only supply input, `Backend` and debug draw. Vendor `vendor:box2d` matches the C repo in `box2d/` (v3.2+ API: `motionLocks`, `base` joint defs, `DrawLineFcn`).

## 3d_models library layout
- `gltf.odin` (package `models3d`: `Model` structs, `ModelLoadGltf`, `ModelAnimate`, skinning helpers), `glTF2/` (copy of the glTF2 parser from third_party/gltf, MIT, patched for current Odin; don't use vendor:cgltf, it clashes with raylib's symbols), `glue_raylib/` glue (`DrawModel` CPU skinning), `gltf_test.odin` (`odin test .`). Assets in `odin_utilities/assets/gltf`.
- Allocator agnostic like atlas_packer: pass an arena to `ModelLoadGltf`, nothing allocates per frame.

## hot_reload library layout
- `hot_reload.odin` (`HotReload*` procs, `Api` that the DLL exports with the `game_` prefix, `LayoutHash`; tests at the bottom build `demo_game` as a DLL), `demo_game/` (framework free demo game DLL, `demo_game/api` is the host proc table), demos in `demo_raylib/` and `demo_karl2d/` (a Reload button rebuilds the DLL and calls `HotReloadRequest`).

## web_build library layout
- `resource.odin` (`ResourceLoad` with `RESOURCE_PATH` / `RESOURCE_EMBED` configs, builds for js so no os/testing there; tests in `resource_test.odin`, disk read in `resource_file.odin`), `web_build.odin` (`WebBuild`, js_wasm32 build of a package with init/step/shutdown, tests at the bottom run a real build), `templates/`. Demos: `demo_raylib/` (desktop), `demo_karl2d/` (`game/` is the web package, `build_web/` calls `WebBuild`).

## web_serve library layout
- `web_serve.odin` (`Server*` procs: static GET/HEAD file server over `core:net`, fixed buffers, polled connections, `ResolvePath` refuses traversal; tests at the bottom use real loopback sockets), `tool/` (`odin run web_serve/tool -- <dir> --open`). No raylib/karl2d demo: nothing is drawn, the tool serves the web_build demo.

## scene library layout
- `asset.odin` (`AssetStore` over a user `AssetStorage(N)`, `LoaderUpdate`: background and blocking requests with a time budget, loaders split in `decode` (may run on a worker thread) and `finish` (main thread)), `asset_workers.odin` (worker pool, `#+build !js`, `asset_workers_js.odin` is the no-thread stub), `prefab.odin` (`PrefabDef` with base and `PatchField` overrides, resolved once), `scene.odin` (`SceneSystem`: scene table, transition, prefetch hints, listeners and scene instances in `core:container/handle_map`, per-scene arena), `glue_karl2d/` glue (loaders, placeholders, `DrawTransition`), `demo_karl2d/`. Builds for js_wasm32, so tests are in `*_test.odin` (`#+build !js`) and not at the bottom.

## serial library layout
- `serial.odin` (binary `Writer`/`Reader` over user buffers with a counting pass, versioned length-prefixed chunks, file frame with crc32, `RleWrite`/`RleRead`; safe on untrusted data, builds for js so tests are in `serial_test.odin`). Used by `tilemap/tilemap_serial.odin` (tilemap layers by name, atlas, tileset), `box2d_odin/physics_serial.odin` (`PhysicsDesc` of bodies, shapes, hinges: write, read with validation, `PhysicsCreate`), `scene/level.odin` (entities as prefab instances with overrides by field path, asset names, `LevelAttach`). `scene/level_integration_test.odin` is the whole level file pipeline.

## signal library layout
- `signal.odin` (`Signal($T,$N,$Q)`: payload, connection capacity, deferred queue size; connections in `core:container/handle_map`, order list kept apart because slots are reused; `Signal*` procs: Connect with `.ONE_SHOT`/`.DEFERRED`, Emit, Flush, Disconnect*, Block; safe to change connections while emitting; builds for js so tests are in `signal_test.odin`), `demo_common/` (framework free model of the demos), `demo_raylib/`, `demo_karl2d/game/`.

## font library layout
- Vector fonts from outlines, two GPU methods: `font.odin` (`Font` over the bytes of a TrueType or OpenType file or collection, metrics in em units, `Method` = `.SLUG` or `.SCANLINE`), `sfnt.odin` + `truetype.odin` + `cff.odin` (the parser, pure Odin: a port of stb_truetype 1.28 that reads a glyph straight into the caller buffer through `OutlineSink`, no allocation, no C library, bounds checked reads; keep it bit for bit equal to stb_truetype, `parser_test.odin` compares every glyph), `outline.odin` (`FontGlyphCurves`: quadratic curves in a caller buffer, `CurvesMonotonic`), `raster.odin` (exact CPU coverage, the reference: `CurvesCoverage`, `CurvesRasterize`), `atlas.odin` (`Atlas` over a caller array of 4 float texels: header rows for the glyph table and a palette of colors, `AtlasGlyph` bakes on demand, `AtlasReserveText`, `AtlasClear`, `AtlasTakeDirty` gives the rows to upload), `slug.odin` + `scanline.odin` (the data of each method and `SlugCoverage` / `ScanlineCoverage`, the CPU models of the shaders), `special.odin` (the missing-character box and the solid glyph), `glyph.odin` (`GlyphInstance`, `EmitGlyph`, `EmitRect`), `atlas_file.odin` (bake ahead, `AtlasWrite`/`AtlasRead`), `rich.odin` (`RichParse`, `RichLayout(&rich, &atlas.faces, ...)`, `RichDraw`: BBCode-like tags and effects; bold and italic faces through `AtlasAddFace`, struck / slanted when a face is missing), `layout.odin` (`TextQuads`: six vertices per glyph with the slot and the palette index, `TextOptions` rotation / snap / wrap, `TextMeasure`), `shaders/` (GLSL 330 for raylib and the GL backend of Karl2D, HLSL for the D3D11 backend: keep each GLSL / HLSL pair the same), glue `glue_raylib/` and `glue_karl2d/` (`Renderer` over a caller vertex buffer, `DrawText`, `DrawRich`, `RendererFlush` with `deferred`, `RendererDraw` of a list, `TextMesh` = a VBO on raylib), `TextSystem` + `TextBox` (a user interface places text by a line box: ui `PainterUseVectorText`, kit `-define:DEMO_VECTOR_TEXT=slug|scanline`, pictures in `captures/<backend>_<method>`), demo `font` (demo_common has a `TextDrawer` hook that demo_raylib and demo_karl2d set), `tool/preview` and `tool/preview_karl2d` (`-- --shot out.png`).
- `odin test font -strict-style -vet` (31 tests, ~0.4 s) and `odin test font/demo_common`. `FONT_TEST_FILES=<a.otf;b.ttc>` compares more font files with stb_truetype (the repository has no CFF font: run it with one after a change to `cff.odin`). `vendor:stb/truetype` of Odin dev-2026-11 has a `fontinfo` that is 8 bytes shorter than the C struct (`vhea`, `vmtx` are missing): the tests pad it (`StbInfo`); nothing else in this repository uses stb_truetype. The shaders are not unit tested: the CPU models are (against the exact rasterizer), the screenshots of both frameworks check the shaders. The Karl2D D3D11 shaders must read every texture through a sampler of the same register (Karl2D checks it) and `point` is a reserved word in HLSL. The Slug shaders are translations of the MIT licensed reference (credit in README and the shader files); the Scanline Sweeper code is written from the paper, not from its MPL listings.

## p2p library layout
- Serverless connection by pasted codes: `stun.odin` (RFC 5389 + CHANGE-REQUEST, pure), `code.odin` (`Invite`: candidates incl. one IPv6, NAT facts; text = Crockford base32 + crc32 over a `serial` Writer), `link.odin` (`Link`: IPv4+IPv6 sockets or a `Transport`, STUN gathering, NAT mapping/filtering measurement, hole punching, port guessing for symmetric NATs, selective repeat reliable channel, events, inbox; fixed capacities, ~320 KB, heap or global; `now_ms` is a parameter), `portmap.odin` (PCP, NAT-PMP, UPnP IGD, blocking and time bounded), `turn.odin` (TURN client, long term credentials, non blocking from `LinkUpdate`), `derp.odin` + `derp_link.odin` (free Tailscale DERP relays, failure kinds + advice, automatic reconnect with backoff, custom relay by name in invites, `tool/derp diagnose|map`: client, pseudo-address candidate, SIGNAL packets so the guest reply needs no pasting, direct-path upgrade), `tls13.odin` (minimal TLS 1.3 client, verified against RFC 8448) + `tls_verify.odin` (server certificate: chain, name, dates, CertificateVerify through core:crypto/x509; roots = two built in from `trust/`, the system store (Windows CryptoAPI / PEM bundles), `P2P_CA_FILE`; on Windows a root the store lacks is looked up through CryptoAPI; `P2P_TLS_VERIFY=off`) + `tls_revoke.odin` (CRL revocation of the chain, `P2P_TLS_REVOCATION=soft|strict|off`), `nacl.odin` (box, verified against the derpnet C code; `references/derpnet` is the reference checkout), `sim_derp_test.odin` (fake relay in the NAT simulation), `relay_find.odin` (`RelayFind`: which TURN servers answer from here, unauthenticated Allocate, list of candidates with free-tier sign-up links), `wireguard/` (separate package: optional encrypted tunnel, keys with core:crypto x25519, installs WireGuard on request, official signed installer on Windows / package manager on Linux, every step logged before it runs, needs administrator rights; Windows and Linux only), `sim_test.odin` (simulated internet: NATs of every mapping/filtering kind, LANs, IPv6 firewalls, STUN with a second address, TURN server; the NAT pair matrix and relay/IPv6 scenarios run there), `tool/chat|probe|portmap|turn|multi` (terminal programs; `multi [n] [chat flags]` starts a host and n-1 guests as processes, passes the codes, merges the output with timestamps and checks everybody heard everybody, up to 8, exit code 0/1; chat has `--find-relay`, `--wireguard [--yes]`, `--wireguard-dry` (whole key exchange and switch without touching the system, used for tests), `odin run p2p/tool/<name>`). No demo_kit demo: it needs a real network and two programs. `proxy.odin` + `proxy_ntlm.odin` + `proxy_sspi_*.odin` + `proxy_tunnel.odin` (http, https, socks5, socks4 proxies through HTTPS_PROXY / ALL_PROXY for the relay; Basic, NTLM, Windows SSPI Negotiate logins), `channel_probe.odin` (is another member the host of a relay channel too). Every packet is sealed with a key from the secret in the invite (`Invite.secret`, `PeerSeal`/`PeerOpen` in link.odin, replay window); a relay of the list that stays down is replaced along `DERP_FALLBACK`. Not for js (core:net); limits and measured free servers in its README.
- `odin test p2p -strict-style -vet` (64 tests, ~3 s, `P2P_LIVE=1` adds a live relay test) and `odin test p2p/wireguard -strict-style -vet` (4 tests), `odin check p2p/tool/<name> -strict-style -vet`. The `Link` and `PortMapState` are too big for a stack: `new(...)` in tests. Tests that use real sockets sleep a millisecond per pump (loopback delivery is not instant); the simulation needs no sleep.
- Findings worth knowing: a real STUN server drops a request whose datagram is longer than its header says (send `request[:length]`); a pipe handed to a child process on Windows keeps the child waiting for end of input (give `clip` a temp file as stdin); the CHANGE-REQUEST result includes the PC firewall.
