# oidc: notes for agents

What is not obvious from the code. The rules for every library are in [../AGENTS.md](../AGENTS.md); the use is in README.md.

- The pure part (`base64url.odin`, `jwt.odin`) must keep building for `freestanding_wasm32` (`odin check oidc -no-entry-point -target:freestanding_wasm32`): a SpacetimeDB module imports it. Everything with crypto, sockets or the OS has `#+build windows, linux, darwin, ...` at the top.
- Keys and tokens live in fixed storage of their structs (`KeySet`, `Metadata`, `Tokens`, `Login`): copying such a struct copies the bytes but not the string headers, which still point into the original: rebase them (`spacetimedb/auth.odin` `rebaseTokens`) or keep the struct where it is. The compiler warns when a procedure returns one by value.
- Only ES256 and RS256 are verified (SpacetimeDB accepts the same two). Never accept the algorithm the token names without checking it against the key kind (`JwtVerify` takes it from the header and picks keys of that kind only).
- `LoginPoll` is not re-entrant: its own requests step `HttpIdle`, which may poll again (`Login.busy`).
- A test that plays the browser and the provider in one thread sets `oidc.HttpIdle` (and `spacetimedb.StreamIdle` when a SpacetimeDB server must reach the provider while the client waits): see `mock/mock_test.odin` and `spacetimedb/auth_test.odin`. The tests of both set globals: they take a lock.
- SpacetimeDB fetches `{iss}/.well-known/openid-configuration` itself, also from `http://127.0.0.1:port` (that is what the tests rely on); it does not check `aud`, the module has to (`module.RequireClaims`). The identity is `blake3(iss|sub)` based: Odin's core has no blake3, so the identity is read from `InitialConnection`, not computed.
- Big locals (a `Login` is about 60 KB, `Tokens` 8 KB, `Request` buffers) go on the heap in tests: a test thread has a small stack.
- Presets (`presets.odin`): Google and Discord are normal OIDC (discovery works, checked live); GitHub is OAuth 2.0 only (no discovery, no ID token, device flow + `Userinfo` of api.github.com, whose token SpacetimeDB cannot take: a broker is the way). `providers.local.txt` is git ignored; the example file and the guide hold only public values.
- Tools are tested, not only run by hand: `tool/login` and `spacetimedb/tool/auth_live` keep their work in `run(arguments) -> exit code` (text through `say`, `capture`, a `Idle` hook), the tests drive them against `oidc/mock` with `--issuer`; `auth_live`'s tests start a real local server (skipped and said without `spacetimedb/tool/setup`). `BrowserLauncher` replaces the start of the browser in tests. The mock has `refresh_secret` (Discord: refresh needs the secret) and `service_secret` (client credentials). Settings files of the tests are written next to the cwd and removed.
- A tool must never print a token: the tests look for `eyJ` and `access-` in the output.
- Opening the browser on Windows (`browser.odin`, found with Discord): `explorer <url>` cuts an address after 259 characters (MAX_PATH) and the login address is about 300, so the PKCE challenge was cut and the provider answered `Invalid "code_challenge"`; `rundll32 ...FileProtocolHandler` and `cmd /c start <url>` start and show nothing from this program. A long address goes into an Internet Shortcut file that is opened with `cmd /c start "" file.url` (`BrowserShortcut`, unique name, `BrowserShortcutRemove`); only http(s) addresses are opened. `write_entire_file` does not shorten an existing file.
- The page that the browser sees at the callback is sent after the code is exchanged and the ID token verified: "Login verified" with issuer and subject, or "Login failed" with the reason (HTML escaped). A callback with another `state`, or an error redirect of the provider (it carries no `state`), is ignored and recorded in `Login.rejected` (the `code` only by its length), which `tool/login` prints.
- Discord: the login works without a secret, refreshing the token does not (`invalid_client`); the ID token carries no `name` (it is in the user info).
- A request buffer holds the whole answer, headers too: a CDN's are kilobytes (Discord's user info answer did not fit 2 KB, so the name was missing). `LoginDisplayName` looks in the ID token and then in the user info (Discord's `preferred_username`); the mock has `header_padding` and `userinfo_name` for tests of it.
- Discord's user info fields (seen live): email, email_verified, locale, nickname, picture, preferred_username, sub.
- Client authentication at the token endpoint (`tokenRequest`): with a secret, HTTP Basic first, then the secret in the form, then no secret at all (a PUBLIC client, SpacetimeAuth `none`, is refused when it sends one: found live, the secret in the settings file made `invalid_client`). `Tokens.client_auth` says which worked and `tool/login` tells the person to delete a secret that is not needed. SpacetimeAuth: ID tokens last 15 minutes, a refresh token needs the `offline_access` scope (in the preset), its user info/ID token name is `Anonymous User` for the anonymous login method.
- `store.odin` keeps the refresh token between runs ENCRYPTED: `protect`/`unprotect` are DPAPI on Windows (`protect_windows.odin`, `Crypt32`, entropy `STORE_ENTROPY`, UI forbidden) and always false elsewhere (`protect_other.odin`): there `StoreAvailable()` is false and nothing is stored, never a plain file (macOS Keychain and the Linux Secret Service are the open work, see TODO.md). The file is `STORE_MAGIC` + the ciphertext; a plain file of the first format (`oidc-store-1`) is overwritten and deleted when read; the buffers are wiped (`StoreWipe`); a value with a line break is refused. `spacetimedb.AuthSessionFromRefresh` turns it back into a verified session (`AUTH_UNREACHABLE` is the only error that is no answer of the provider). The mock has `rotate_refresh` and `RevokeRefreshTokens`.
- One store file per provider (`StoreVariant`), the newest by `StoreModified` is the default at the next start: a single shared file made the window that signed in last overwrite the sign in of the other window.
- Device flow (GitHub, found live): a poll that comes before the provider's interval is answered `slow_down` and asks for 5 s more; the next poll must be counted again from now with the new interval (`deviceSchedule`, plus one second of margin), else every later poll is early too and the approval is never seen. `tool/login github --verbose` prints what GitHub answers at each change. The tool's default wait is 300 s (`--timeout`), shorter than the 15 minutes of the code.
- GitHub in the browser (`ClientConfig.oauth_only`, live 2026-11-25): authorization code + PKCE (S256, supported by GitHub since 2025), the secret at the token exchange (GitHub asks for it, public clients are not distinguished), no nonce, no ID token: `LoginPoll` takes the access token and fetches the user (`LoginUserinfo`, name from `name`/`login`); the callback address must be registered exactly (`http://127.0.0.1:48217/callback`). Without `github.client_secret` the tool falls back to the device flow and says so. SpacetimeDB cannot take the access token: a broker is still the way for a game.
- The timeout of a request (15 s) is multiplied by `oidc.TimeScale` (`ODIN_SLOW`, see `wait_for`; `time_scale.odin`).
