# spacetimedb/arena: notes for agents

What is not obvious from the code. The rules for every library are in [../../AGENTS.md](../../AGENTS.md), `spacetimedb` in [../AGENTS.md](../AGENTS.md), the use in README.md.

- Layers: `module/` (the game in the database, Odin wasm) -> `schema/` (GENERATED, never edit: `odin run spacetimedb/arena/tool/schema` after the module changed; it starts a server) -> `game/` (client logic) -> `session/` (p2p: host, guest, tunnel) -> `demo_common/` (window).
- Build the module with `odin run spacetimedb/tool/build_module -- spacetimedb/arena/module spacetimedb/bin/arena-odin.wasm` (the setup does it too: `SetupOdinModule` looks in `module/example/<name>` and in `<name>/module`).
- The blocking calls of the client (HTTP, the websocket handshake) through a tunnel need the same thread to step the tunnel: `session.SetIdle` sets `spacetimedb.StreamIdle`. A host process steps itself in its frame loop. If a join hangs, look there first.
- A host keeps its database in `<root>` and the owner identity in `<root>/owner.token`: without the token a second start cannot update the database ("not authorized").
- Tests start servers on ports 3143 to 3145 (and 3144 live); the folders are removed with `spacetimedb.ServerRemove` (the database files are locked for a moment after the kill).
- `Host`/`Guest` structs go on the heap in tests: `SetIdle` keeps pointers to them (the compiler warns about stack addresses).
- The demo reads `os.args` once (`parseArguments`); a test sets `config` itself (`parsed = true`) and `sleep_ms` because a headless run has no real time for the network.
- A test that is killed leaves `spacetimedb-standalone.exe` running on its port; the next run then talks to the old server ("not authorized"): kill the orphans (`taskkill /F /IM spacetimedb-standalone.exe /IM spacetimedb-cli.exe`).
- The stdin reader of a host is a thread with a one slot mailbox (`console.odin`), the only thread of the game.
- The start screen is in `demo_arena.odin` (`Phase.MENU/JOIN_FORM`, `pending` is done in the next update so that "starting..." is drawn first). Command line arguments skip it (`config.menu`). Its test is `script_menu.odin` (clicks at fixed places of the 1280 x 720 screen: move a widget and the script moves with it) and the two tests share the demo state, so they take `tests_lock`.
- `ServerStop` waits until the port answers no more: a server that starts right after on the same port (Escape then Host a game) used to find the old one and time out.
- The windows are made with the `ui` library (`screens.odin`: start screen, code form, connecting steps, Players and Connection windows; the field and the coins are kit drawing). `ui` names are ids: the Connection window is `CONNECTION_WINDOW` (`"Connection##connection"`), and the scripts find widgets with `aim(window, widget)` from the layout of the last frame (`script_menu.odin`), never by pixels. `UiLabelText` shows the value before the label: use `UiLabel` with a formatted text. A code has no spaces and cannot wrap: `cutCode`.
- The session is staged and never blocks after the server started: `HostBegin`/`GuestBegin` then `HostUpdate`/`GuestUpdate` move `Stage` (GATHERING, RELAY, READY, CONNECTED); `HostStart`/`GuestJoin` are the same with a waiting loop (CLI, tests).
- `captures/<backend>/start_screen.png` are the goldens of the start screen (`-define:DEMO_TEST=true -define:DEMO_CAPTURE=true`; the script sets the name to `player` so no user name is in the picture).
- Window tests go through the tool, never `odin run demo_raylib -define:DEMO_TEST=true` by hand (that opens on whatever display is the default): `odin run demo_kit/tool/captures -- --karl2d spacetimedb/arena` puts the windows on the display of `demo_kit/monitor.txt` (BenQ), `-- --update` replaces the pictures. Nine pictures per backend: join_form, menu_refused, connecting, host_ready, host_with_friend, guest_playing, signin_providers, signin_waiting, signed_in; codes are masked (`config.mask_codes`) and the right panel is captured with `CaptureIn` (the field changes all the time).
- p2p is used the way ai_messaging does: `include_loopback` always, the relay chosen with `DerpRace` before the gathering, the host waits for the relay before making the invite, and the events of the link are read every update (`linkEvents`: relay failed/switched/lost, friend joined/left, nobody answered) and shown as a notice in the Connection window.
- `ServerStop` waits until the process has let go of its log file: a server started right after with the same log file used to fail silently (its redirection could not open the locked file) and the next `HostBegin` timed out.
- Rooms (`HostOptions.room`, `HostRoom`, `GuestBeginRoom`): the host is the key `DerpChannelKey(name)` at the relay (`link.config.derp_private` before `LinkDerpBegin`), the room code is `name-<relay number>` because both sides must use the same relay; the guest `LinkDerpFind`s the key and gets the host's invite in `link.derp.found` (event `DERP_HOST_FOUND`). The name is the secret of the room. `looksLikeRoom` tells a room name from an invite code. Needs the internet: tested with `ARENA_LIVE=1`.
- Pictures wait 15 frames before a capture: widgets fade on hover and focus, and a capture taken in the middle of a fade differs by a few hundred pixels from run to run.
- Signing in (`signin.odin`, screens in `screens.odin`, test `script_signin.odin`): the start screen has Sign in / Sign out; the accounts are the ones of `oidc/providers/providers.local.txt` with a client id (Google, Discord, SpacetimeAuth) or `config.signin_providers`. The login is `oidc.LoginBegin/LoginPoll` once per update (phases SIGN_IN, SIGNING_IN, SIGN_IN_WAIT); on DONE `AuthSessionFrom` keeps the tokens, the name of the account (`LoginDisplayName`) becomes the player name, and `GameOpen(..., token, refresh, refresh_user)` connects with the ID token: the identity in the database is then the one of the person (same on every server and computer), an anonymous player gets a new one every time. The server has to reach the provider (internet) to check the token. The test runs a provider of our own (`oidc/mock`), plays the browser, and starts real servers: two solo games give the same identity, an anonymous one another. `oidc.BrowserLauncher` is replaced in the script (no real browser), and `session.ClearIdle` (leaving a game) also removes `spacetimedb.StreamIdle`, so the script puts its hook back before each game. Three pictures: signin_providers, signin_waiting (the address is masked), signed_in.
- The sign in is remembered (`signinSave`, `signinRestoreBegin`, `signinRestore` in `signin.odin`, `config.signin_store`): the refresh token goes to `oidc.StorePath("odin_utilities_arena")` after a login and whenever the provider rotates it (`signinKeepStored`, every update), the next start restores the account without the browser (phase SIGNING_IN with `signin.restoring`), Sign out deletes the file, a refused token deletes it and says so, an unreachable provider keeps it. The default path is set in `parseArguments` only when not `kit.DEMO_TEST`: a stored login of the person who runs the tests or the pictures must not change them; the script sets a path of its own (`arena_test_signin_store/`). Covered by `script_signin.odin`: written, restored after a restart (same identity, no browser, rotated token), sign out, revoked, offline, another client id, garbage file.
